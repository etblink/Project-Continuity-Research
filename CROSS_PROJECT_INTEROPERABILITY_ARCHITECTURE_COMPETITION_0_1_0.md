## 1. Competition rule

No architecture receives credit merely because it resembles Project Observatory, CCP, or an existing implementation.

All candidates are evaluated against the same:

- 30 frozen requirements;
- 24 frozen threats;
- 8 frozen adversarial conformance cases;
- complexity and adoption burden.

A candidate that passes by embedding project-specific special cases is not project-neutral.

## 2. External standards reconnaissance

The competition does not assume the transport and provenance layers must be invented from scratch.

Relevant mature mechanisms include:

### CloudEvents

The current stable CloudEvents core specification is v1.0.2.

Useful transferable concepts:

- event ID;
- source;
- event type;
- specification version;
- event data;
- transport-neutral event description.

CPI should reuse these ideas if an event stream is selected rather than creating an incompatible generic event envelope.

CloudEvents does not determine:

- whether an event is canonical;
- whether authority is transitive;
- whether the receiving project accepts the event;
- project-specific negative knowledge;
- project-local scientific or product governance.

### in-toto Attestation Framework

The current attestation framework identifies v1.2 as the latest specification line.

Useful transferable architecture:

- Subject — the artifact/object being described;
- Statement — binds subject to a typed predicate;
- Predicate — domain-specific metadata;
- Envelope — authentication/serialization;
- Bundle — grouping attestations.

The framework recommends DSSE-style authenticated envelopes.

This architecture is highly relevant to CPI because it separates generic identity/authentication from domain-specific predicates.

CPI should not claim this layering as novel.

However, software-supply-chain attestation does not itself define project-local canonicalization or remote/local authority firewalls.

### W3C PROV-O

W3C PROV-O remains a stable W3C Recommendation for expressing provenance among:

- entities;
- activities;
- agents;
- derivation;
- attribution;
- generation and usage.

CPI can reuse provenance semantics without requiring RDF/OWL as its wire representation.

### Standards disposition

CPI should be standards-friendly rather than standards-dependent.

The architecture competition therefore evaluates project-governance semantics first and treats envelope, authentication, and provenance serializations as replaceable implementation layers.

## 3. Candidate A — Minimal Project State Projection

### Model

Each project exposes one small immutable point-in-time projection.

A projection contains:

- project identity;
- exact source identity;
- authority-purpose map;
- current high-level state;
- evidence references;
- negative knowledge;
- dependencies;
- triggers;
- next-transition status;
- freshness identity.

The projection may be authored natively by the project or generated by a read-only adapter.

### Strengths

- very simple consumer model;
- excellent current-state orientation;
- strong freshness and snapshot semantics;
- compatible with EBMM and PGH;
- can represent NFC authority routing explicitly;
- easy to archive and diff;
- preserves project independence;
- low operational burden.

### Weaknesses

- changes between projections have no first-class event identity;
- trigger delivery is polling-oriented;
- difficult to prove whether omission is no-change or projection loss;
- replay/idempotence semantics are indirect;
- event-level authority changes and local import outcomes become awkward;
- rich causal provenance tends to accumulate inside a growing projection.

### Conformance result

Passes the static-state cases well.

Weaker on:

- R07 provenance-preserving transformations;
- R20 verification/read-back over transitions;
- R28 replay/duplicate safety;
- cross-project trigger routing.

Disposition:

VIABLE_BUT_INCOMPLETE_AS_SOLE_PROTOCOL

## 4. Candidate B — Typed Event-Envelope Federation

### Model

Projects emit typed immutable cross-project events.

Generic envelope fields resemble established event standards:

- event ID;
- source project;
- source revision;
- event type;
- time;
- protocol version;
- subject;
- typed payload/predicate;
- integrity/authentication metadata.

Consumers maintain their own local projections from received events.

### Strengths

- excellent change identity;
- natural idempotence/replay handling;
- good for trigger routing;
- authority and verification events can be separate;
- maps well to CloudEvents and attestation standards;
- append-only history is auditable.

### Weaknesses

- new consumers must replay or obtain a checkpoint;
- project state may be underdetermined if events are missing;
- negative knowledge can become fragmented across many events;
- projects not already event-sourced require adapters that infer events from repository changes;
- historical repository state before adoption is difficult to reconstruct cleanly;
- event feeds tempt consumers to treat delivery as authorization.

### Conformance result

Passes transition-oriented requirements well.

Weaker on:

- simple cold-start orientation;
- federation optionality for repositories with no native event stream;
- omission/completeness detection;
- frozen point-in-time state.

Disposition:

VIABLE_BUT_INCOMPLETE_AS_SOLE_PROTOCOL

## 5. Candidate C — Provenance-Graph Exchange

### Model

Each project exports or exposes a typed graph containing entities such as:

- claims;
- evidence;
- artifacts;
- events;
- authorities;
- policies;
- dependencies;
- negative-knowledge objects;
- transitions;
- snapshots.

Relations include concepts such as:

- derived from;
- supported by;
- attributed to;
- authorized by;
- supersedes;
- blocks;
- reopens;
- observed at;
- accepted by.

The graph may reuse W3C PROV concepts where appropriate.

### Strengths

- strongest representation of provenance and dependency;
- excellent scoped supersession;
- contradictions and multiple authorities can coexist;
- good for FCP, Observatory, and CCP-like semantics;
- naturally supports audit queries.

### Weaknesses

- highest conceptual burden;
- risks turning the common protocol into a universal ontology;
- difficult for simple projects such as EBMM;
- projection freshness and current-state orientation still require conventions;
- graph merge semantics can become governance semantics by accident;
- likely to centralize meaning in the Observatory's ontology;
- poor first adoption path.

### Conformance result

Semantically powerful but violates the research-economy requirement unless evidence proves the complexity necessary.

Primary risk:

THE_PROTOCOL_BECOMES_MORE_COMPLEX_THAN_THE_PROJECTS_IT_ORIENTS

Disposition:

REJECT_AS_MANDATORY_CORE
RETAIN_AS_OPTIONAL_INTERNAL_OR_EXTENSION_MODEL

## 6. Candidate D — Query-Only Federated Observatory

### Model

No project publishes a standard export.

The Observatory reads repositories directly through project-specific adapters and reconstructs current state on demand.

No cross-project protocol exists beyond a common Observatory query API.

### Strengths

- zero required mutation of observed projects;
- easiest immediate deployment;
- excellent fit with current Project Observatory;
- projects remain fully independent;
- can inspect exact native artifacts;
- useful research instrument.

### Weaknesses

- project-specific adapter logic becomes the hidden protocol;
- adapter behavior may be difficult to audit across projects;
- changes in repository layout break interpretation;
- authority resolution is centralized in adapter code;
- pairwise special cases accumulate;
- external triggers require polling or separate infrastructure;
- consumer cannot distinguish native semantics from adapter interpretation without deep provenance;
- maximizes observer-oracle risk.

### Conformance result

Strong research/bootstrap approach, weak public interoperability protocol.

Disposition:

ACCEPT_AS_BOOTSTRAP_AND_LEGACY_ADAPTER_STRATEGY
REJECT_AS_FINAL_PROTOCOL_CORE

## 7. Candidate E — Hybrid Attested Projection + Typed Event Federation

### Model

Candidate E combines two complementary objects while preserving local project governance.

### Layer A — Project Projection Attestation

A point-in-time immutable projection answers:

- who/what project is this;
- what exact source identities are in scope;
- what sources are authoritative for which purposes;
- what objects are currently material;
- what negative knowledge is active;
- what dependencies/triggers constrain state;
- what next-transition states exist;
- when this projection was observed.

The projection is an attestation about project state, not the project state itself.

### Layer B — Typed Project Events

Optional immutable events describe material changes such as:

- projection published;
- authority mapping changed;
- candidate opened;
- candidate accepted/rejected;
- dependency changed;
- trigger satisfied;
- hold opened/reopened;
- external verification changed;
- local import accepted/rejected.

Events reference exact source and projection identities.

### Layer C — Local Import Adjudication

Receiving projects never ingest remote objects directly as canonical state.

They create a local import record with a local disposition such as:

- evidence_only;
- trigger_candidate;
- dependency_update_candidate;
- contradiction;
- quarantined;
- rejected;
- accepted_for_local_scope.

Only a separately valid local transition may change local canonical state.

### Layer D — Provenance relations

A minimal relation vocabulary records source and derivation.

Full provenance graphs are optional.

The protocol may borrow W3C PROV concepts without requiring every project to publish an RDF graph.

### Layer E — Adapter compatibility

Projects that do not natively publish projections/events may participate through a read-only adapter.

The adapter must identify itself as the producer of a derived projection and preserve the underlying project source identities.

This allows gradual adoption and makes current Project Observatory useful as an experimental adapter host.

## 8. Why projection and event are both necessary

Projection solves:

- cold start;
- current orientation;
- negative-knowledge completeness;
- freshness checkpoint;
- project-native state diversity.

Event solves:

- change identity;
- replay/idempotence;
- trigger routing;
- authority-change notification;
- transition verification;
- incremental synchronization.

Neither object is canonical merely because it exists.

The project-local canonical state remains upstream.

## 9. Candidate-E authority firewall

The core rule is:

REMOTE ATTESTATION
!=
LOCAL ACCEPTANCE
!=
LOCAL AUTHORIZATION
!=
LOCAL CANONICAL MUTATION

Every consequential consumer must preserve those four layers.

No transport layer may collapse them.

## 10. Candidate-E standards strategy

Candidate E should not create new generic envelope cryptography.

Preferred direction for a later prototype:

- event context compatible in spirit with CloudEvents;
- subject + typed predicate + envelope compatible in spirit with the in-toto Attestation Framework;
- provenance relations aligned where useful with W3C PROV concepts;
- Git commit/tree/blob identities used directly where Git is the authoritative evidence source.

A prototype may initially use content hashes and exact Git identities without deploying a full signing PKI.

Cryptographic authentication should be layered separately from semantic validation.

## 13. Complexity discipline for Candidate E

Candidate E is selected only under a strict minimum-core rule.

The first prototype must not implement:

- a graph database;
- a message broker;
- a PKI;
- distributed consensus;
- automatic cross-project writes;
- a universal ontology;
- a workflow engine;
- a hosted service;
- a new repository daemon.

A file-backed read-only simulation is enough.

The prototype should prove semantics before infrastructure.

## 14. Candidate-E minimum core

The minimum semantic core for simulation is:

1. ProjectDescriptor
   - project ID;
   - authority-purpose mappings;
   - supported protocol version.

2. ProjectProjection
   - immutable projection ID;
   - observed source identities;
   - observation time;
   - material object summaries;
   - negative knowledge;
   - dependencies;
   - triggers;
   - next-transition statuses.

3. ProjectEvent
   - stable event ID;
   - source;
   - event type;
   - subject;
   - source/projection identity;
   - typed payload;
   - time.

4. ImportRecord
   - remote object identity;
   - receiving project;
   - local disposition;
   - local authority;
   - local scope;
   - reason;
   - resulting local transition, if any.

5. DerivationRecord
   - inputs;
   - transformation version;
   - output;
   - unresolved ambiguity.

No additional core object should be added without a failed conformance test that requires it.
